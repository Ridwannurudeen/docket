**Scope:** branch `feat/stage2-action-kernel`, commits 8985eda, 477455a, 87fe874, fbdd742, 247914d, 6229e68, 3e83e01, 9e02567 on top of f89fc48. Audited 2026-08-10 against the plan (`docs/plans/2026-08-18-stage2-action-kernel-grid.md`). Safety first, strategy second, per the brief: this is the stage that touches money.

**Method.** Full suite run on the branch (571 passed, 32.7s); base collected in a throwaway worktree (370 exactly; worktree removed; `git status` clean after). Every Stage 2 source and test file was read in full. The two key-identifier derivations were re-derived by hand from raw bytes and checked against the helpers, with the keccak implementation itself first validated against public vectors ("abc", "testing") and four universally known selectors (`approve` 095ea7b3, `transfer` a9059cbb, `swapExactTokensForTokens` 38ed1739, `getAmountsOut` d06ca61f — all matched). Nothing was pushed, deployed or submitted.

## Verdict: MERGE WITH FIXES

The code is the strongest work on this repository so far, and I could not break the four properties I was sent to break. No cap, allowlist or expiry is enforced only server-side; no path submits an action whose live simulation disagreed; a revoked or expired session cannot act and every refusal fails closed; and the preview is structurally — not configurationally — incapable of submitting. The two key derivations, flagged by the builder as the likeliest silent wrong answer, are correct: hand-computed here byte-for-byte and matched structurally against the canonical upstream source. Both required fixes are in the runbook, not the code — and the runbook is a deliverable of this stage (Task 6), it is the document a user acts on with real money, and the merge window is where a doc fix is free. One instruction in it can brick the proof, and the single most important warning about the whole enforcement claim is missing from it.

## Tier 1 — required before merge (both are runbook edits)

### F1 (MEDIUM): §7.4's "owner **or session**" approve is an instruction that can dead-end the proof

`docs/runbooks/grid-mainnet-proof.md:218-221` says the USDT approval may be signed by "owner or session", sized "for exactly the cap" (30 USDT). Read from the canonical GuardedExecutor source this build's ABI was matched against (`GuardedExecutor.sol:272-280, 313-319`, fetched from ithacaxyz/account main):

- **Any non-zero `approve` executed through a session key is automatically revoked to zero at the end of that batch** ("we need to make sure that approvals are revoked. This is to prevent sidestepping the guard"). A session-signed approve as a separate step therefore leaves **no allowance behind at all** — §7.5's swap then reverts on `transferFrom` regardless of anything Docket did.
- The approve's full amount is also **counted against the spend cap** (`t.transferAmounts.p(... amount)` at `GuardedExecutor.sol:279`; the period's spend is `max(declared calldata amounts, actual balance decrease)` at `:340-346`). A session-signed `approve(router, 30e18)` consumes the entire 30 USDT/day cap in one move; the swap is then refused — by the chain, and by Docket's own `check()` reading `remaining_cap` = 0.

Whether Altana's deployed account (23,384 bytes at 0x4B5d20CD…, source unpublished) keeps these exact semantics is not verifiable — the runbook already owns that footing at `:304-310` — but the fix is correct under **either** semantics: **§7.4 must say the approve is owner-signed**, and may add that if a session-signed approve is ever used it must be batched with the swap it feeds and will be zeroed after the batch. Every failure mode here is a refusal or a revert — no value can be lost — so this is proof-reliability, not fund-safety; but a runbook whose step 7.4 can silently guarantee step 7.5 fails is not yet safe to hand a user, and §4's testnet rehearsal should not be the way they find out.

### F2 (MEDIUM): the one sentence that protects the entire enforcement claim is missing

`canExecute` returns true unconditionally when `keyHash == 0` — "the execution is authorized / performed by the EOA's secp256k1 key itself" — and for any super-admin key (`GuardedExecutor.sol:469-480`, canonical source). Every on-chain limit this stage stands on — cap, allowlist, expiry, revocation — binds **only execution signed by the session key.** The runbook's §7.5 (`grid-mainnet-proof.md:225-229`) does instruct a submitter that "signs the intent's calldata with the session key and sends it through Altana's relay", which is the right instruction; what neither the runbook nor `operator.py` states is the consequence of deviating: **a submitter wired to the owner key (or any super-admin key) silently voids every on-chain limit**, leaving Docket's Python checks as the only gate — the exact configuration the stage's first rule forbids — and Docket cannot detect it, because the submitter is an opaque callable (`operator.py:404`) and the session's on-chain cap would never decrement, so `check()` would keep passing forever.

Fix: one paragraph, in §7.5 and/or the `GridOperator` docstring (`operator.py:272-278`): *the submitter must sign with the session key; an owner-key submitter is not a shortcut but the removal of every limit this proof exists to demonstrate.* The code needs no change — this is a property of account abstraction, not a bug — but the claim "enforcement is on chain and is not Docket's" is true only on the session path, and the document a user follows must say so.

## Tier 2 — recommended, non-blocking

### F3 (LOW): §1's sixth proof item promises more than §8's check 6 performs

`grid-mainnet-proof.md:24-25` says the post-revoke attempt is "refused — and refused by the chain, not by Docket being polite about it." Check 6 (`:256`) as specified re-runs 7.2 and 7.5 and observes `can_execute` return `(False, "revoked…")` with the submitter never reached — which **is** Docket refusing, on the strength of a chain read (the key gone from `getKeys`, `isValidKey` false). The chain's own rejection of an actual attempt is never demonstrated, and that is the **right** choice: firing a real post-revoke transaction to prove the refusal would be a value-moving call whose safety depends on the very revocation being tested — the one thing this repository never does to "check". But then §1.6 should say what check 6 shows: refused on the chain's own recorded state, from which the validator's rejection follows, rather than implying a rejected live attempt. One sentence.

### F4 (LOW): the armed operator keeps no fill memory and does not hand back the level it fired

`operator.py:326` — `step(*, filled=(), nonce: int = 0)`. The caller owns fill-tracking (documented on `next_action`, `plan.py:230-232`, but not on `step()`), and the step record does not surface the fired level's index as a first-class field — a caller must parse it out of `intent_id` or the condition. A loop calling `step()` with the defaults re-fires the same level on every observation until the on-chain cap stops it: with the runbook's own numbers (30 USDT cap, 5 USDT/level) that is up to six duplicate fills, all inside authority, each individually bounded by its own live-quoted `min_output`. The backstops (cap on chain, floor in the calldata) hold, Docket ships no submitter and no loop, so nothing today can hit this — but the operator is the piece a future loop will be built on. Cheap fix: return `level_index` in the step record and add one sentence to `step()`'s docstring saying `filled` and `nonce` are the caller's ledger.

### F5 (LOW): the runbook cites two version numbers for one contract

`grid-mainnet-proof.md:260` grounds monotonic revocation "in Altana v1.0.0"; the deployed KeyStore's `VERSION()` reads `1.0.1` (verified live this session; also `authority.py:52-53` and the runbook's own §11 at `:317`). If monotonicity was established from v1.0.0 documentation, say that; as written the document contradicts itself on which version the property was checked against.

## The assigned questions, answered

**(a) Is any cap, allowlist or expiry enforced only server-side?** No. The enforcement chain was traced to its source rather than taken from the module docstring: the wallet's own `canExecute(keyHash, target, data)` and `spendInfos(keyHash)` are the chain's answers (both selectors present in the deployed 23,384-byte account implementation; struct layout `(token, period, limit, spent, lastUpdated, currentSpent, current)` confirmed against the canonical `GuardedExecutor.sol:54-69`, so `remaining = info[2] - info[5]` at `authority.py:720-725` reads the right fields and the timestamp trap named in the code — `current` is a period start, not a balance — is real). What Docket reads from chain versus assumes locally is exactly as documented: `valid` (isValidKey), `revoked` (key absent from getKeys), `remaining_cap` (spendInfos) and `call_allowed` (canExecute) are chain answers; `expiry` on the status is the owner's recorded grant (`SessionRef.expiry`, `authority.py:276-278`) — and a wrong record fails closed, because the chain's own expiry enforcement arrives through `isValidKey` and through the account's signature-validation expiry check (`IthacaAccount.sol:517-518`). Docket's local copy of the allowlist runs **after** the wallet's `canExecute` and can only refuse more (`check()`, `authority.py:353-409`; `call_allowed is False` outranks at `:383-387`); "no cap" refuses rather than passes (`:396-400`); an unreadable chain refuses (`:766-772`); an undelegated wallet is its own typed refusal (`UndelegatedWallet`, `:556-562, 620-627`). The one deployment that voids all of this — an owner-key submitter — is F2, a documentation gap, not a code path Docket ships.

**(b) Can an intent be submitted whose live simulation disagreed with its bounds?** No path found. The repository's only submission call site is `operator.py:404`; repo-wide grep confirms the only signing/sending code anywhere is `escrow/settle.py:148-159` — pre-existing, `DOCKET_SETTLE_KEY`-gated, aimed at the ERC-8183 router's `settle()`, and imported by nothing in `execution/`, `agents/grid/` or `hire/`. Line 404 sits behind two gates in sequence: `result.agrees` (`:371-375`, else `paused` with the reason) and the authority's fresh `can_execute` (`:395-401`, else `paused` with the reason). `Simulation` cannot claim agreement without knowing the output (`simulate.py:117-122`), cannot agree below the floor (`:229-242`), cannot agree past the gas ceiling when a sender exists (`:258-269`), and refuses first of all when the bytes are not the committed bytes (`:187-199`). The floor is not merely checked but **carried**: `min_output` is encoded into the calldata itself (`swap_calldata`, `simulate.py:67-103`, which independently refuses a zero floor), so the router re-enforces it on chain at execution even if everything off-chain were wrong, and the calldata is hash-committed into the intent (`intent.py:214-227` — selector and digest must both agree). Tests assert the submitter was never called on each refusal path, not merely that the result said no (`test_grid_operator.py:277-337`).

**(c) Can a revoked or expired session still act?** No. Revocation: read fresh from chain at decision time (`can_execute` → `status` → `getKeys`, `authority.py:714-716, 761`), reported as `revoked` when the id is gone from the list — the same-transaction removal the docstring describes — and refused ahead of every other reason (`check()` order, `:372-373`); monotonic in the stub as on chain (`test_execution_authority.py:265-274`); and the state machine gives `revoked` and `expired` no outgoing edges at all, proven by the exhaustive 100-pair matrix (`test_execution_state.py:200-213`), so no lifecycle path re-reaches `submitted`. Expiry: triple-covered — the chain's `isValidKey`, the recorded `expiry <= now()` refusal, and the sharper `intent.deadline > status.expiry` refusal (`authority.py:376-380`) that stops an action which would be mined into an unauthorised window. The builder's "status read twice, decision uses the fresher read" description is accurate (first read at `operator.py:379` feeds the receipt; the deciding read is inside `can_execute` at `authority.py:761`); the residue is F7, cosmetic. Between decision and broadcast there is an unavoidable window — and that is exactly what the on-chain validator exists to close, which is the design.

**(d) Is the dry-run genuinely incapable of submitting?** Yes, and I tried to find a route. Verified live: `GridPreview.__mro__` is `['GridPreview', 'object']`; its class body holds only `_observe` and `preview`; a constructed instance's `vars()` are exactly `plan, wallet, _reader, _slippage_bps, _gas_ceiling, _policy_version` — no submitter, no authority, no ref, no key, matching the builder's claim to the letter. Neither class inherits from the other (asserted at `test_grid_operator.py:197-198`). `preview()` reaches the network only through the injected reader, and the shipped reader (`BscQuoteReader`, `simulate.py:135-169`) exposes only `getAmountsOut`, `eth_estimateGas` and `block_number` — and `simulate()` is called with no sender from the preview (`operator.py:248`), so even the gas estimate is never attempted. The hire path a stranger reaches (`_run_grid_operator`, `catalogue.py:129-166`) constructs `GridPreview` only, source-pinned by test (`test_grid_operator.py:417-440`); the armed class refuses construction without authority+ref+permissions **and** a submitter, before any node is contacted (`operator.py:293-306`), and Docket ships no submitter. Environment variables arm nothing (`test_grid_operator.py:201-208`). I ran the real hire path against BSC mainnet: six levels drafted and quoted at block 115,167,408, `submitted: false`, `authority: null`, checks `['intent.matches', 'router.getAmountsOut']` and no gas figure on every level. The only send in the repository outside the injected callback is `settle.py`'s, unreachable from here. I found no route from preview to a transaction.

**(e) The two key-identifier derivations.** Both verified independently, two ways. **By hand:** with the keccak implementation first validated against public vectors and four known selectors, `keystore_key_id` equals keccak over the raw 65 bytes and nothing else (refusing 33-byte and non-0x04 inputs), and `account_key_hash` equals `keccak( 32-byte big-endian 2 ‖ keccak( 12 zero bytes ‖ 20-byte address ) )` built from raw bytes — both matching the helpers exactly, the two identifiers distinct, a lowercased address deriving the same hash, and `abi.encode(uint256,bytes32)` = `abi.encode(uint8,bytes32)` = the hand-built 64 bytes, confirming the code's "a uint8 and a uint256 ABI-encode alike" note. **Against canonical source:** `IthacaAccount.sol:44-49` fixes the enum (P256=0, WebAuthnP256=1, **Secp256k1=2**, External=3 — `KEY_TYPE_SECP256K1 = 2` is right); `:443-445` fixes the hash as `keccak256(abi.encode(key.keyType, keccak256(key.publicKey)))`; `:536-538` fixes a Secp256k1 key's `publicKey` as `abi.encode(address)` — i.e. the 32-byte left-padded address — which is precisely `authority.py:173-175`. The four Altana selectors hand-computed here (8fd4f06b, 34e80c34, dcc09ebf, ff619c6b) match the test file's independently hardcoded values (`test_execution_authority.py:602-615`) and are all present in the deployed runtime bytecode (KeyStore and account implementation, re-checked this session at block 115,166,876). A wrong derivation also fails **closed** in every mixed-up direction — a bad `key_id` reads as invalid/revoked, a bad `key_hash` reads as no caps and no permission — because the dangerous answer would require the wrong hash to collide with a different registered key. What hand-verification cannot reach: whether the KeyStore's `keyId` really is keccak of the SEC1 public key is transcribed from Altana's SDK and has never been read against a live granted key — which is stated, in the gap, the runbook and the module docstring.

**(f) Honesty of the Altana claim.** `integration_gap()` (`authority.py:670-696`) is accurate and, with F2's consequence sentence added, complete. Plane 1 (enforcement on chain, not Docket's): true, and now traced to the canonical validator source rather than to documentation alone. Plane 2 (verification real from Python, no SDK in the path): true — the four reads exist, are plain `eth_call`s over the existing failover, and were exercised live this session, including `isValidKey` = false and `getKeys` = () for a keyless address, matching the code's documented empty-state behaviour. Plane 3 (grant/revoke/submit deliberately absent): true — both methods raise `IntegrationGap` (`:775-787`), grep finds no signer anywhere in the package, and the stub announces itself in-band (`source: "stub"`, empty `reads`, test-pinned). The three travelling caveats all check out: the ABI-from-SDK-not-source footing is stated; the never-exercised-against-a-live-session admission is stated in three places; the `register=false` invisibility trap is stated and drives the runbook's "MANDATORY" flag. Nothing in code, docs or UI overclaims — the marketplace record's first breath is that a hire previews rather than trades (`registry.py:49-87`), llms.txt says the same where it stocks the shelf (`llms.txt:506-514`), and even the runbook's packaging trivia survived independent checking: `@altananetwork/sdk@0.7.0` exists on npm, its `repository.url` (github.com/altananetwork/sdk) 404s, the real repository is `altananetwork/altana-sdk`, and the license really is split — GPL-3.0-or-later on the registry against Apache-2.0 on GitHub. Exactly as written.

**(g) Grid correctness.** The plan hash is SHA-256 over canonical JSON of the inputs **and** the derived levels (`plan.py:98-120`), so a derivation change alters the digest even at identical inputs — tested, along with per-input change detection. Spacing is floor-division over the whole span (`:176`), so the last level lands exactly on `upper` and no level accumulates error; a level on the reference is dropped and counted (`skipped_at_reference`) rather than given an arbitrary side. Re-fires: `next_action` honours `filled` and fires the nearest reached level (`:221-246`), tested; the operator-level residue is F4. The marketplace record states its limitations truthfully — V2 exact-input only, preview-only structurally, session required for action, fill-is-not-a-gain, no measured figures so none published, deterministic-not-adaptive (`registry.py:68-86`) — and `activation` is `one_shot`, refusing the tempting `policy_action` with the reason in a comment.

## Would I let a user grant a real session to this code today?

Split, because the question is two acts. **Granting the §5 session — yes.** A 30 USDT/day cap, a two-entry call allowlist, a 24-hour expiry, owner-held revocation that is monotonic on chain, against code where every observed failure mode refuses closed and where nothing Docket ships can sign or send: the bounded downside is the cap, and the cap does not depend on Docket being correct. **Running the mainnet proof today — no.** The read path has never seen a live granted session (the build's own stated gap), the testnet rehearsal that exists to close exactly that has not happened and its addresses are unverified from here, and the runbook still contains F1.
