## Tier 1 — required before merge (all are prose edits)

### F1 (MEDIUM): llms.txt still says "Three of the four services" have no identity — it is now five of six

`docket/api/static/llms.txt:546`: under `agent_id null` — "Three of the four services are in this state." There are six services on this branch (llms.txt's own line 493 says so correctly) and **five** carry `agent_id=None` (`registry.py:56, 92, 126, 163, 290`; only solvent-signal is bound, `:234`). This is the exact regression class the stage was told to sweep — the builder caught the two inventory sentences ("three of the four are empty") and their drift guards now hold both branches (`test_services_api.py`, llms.txt guard), but this identity-count sentence has no guard and went stale the same way. Fix: correct the sentence, and preferably bind it the way the inventory sentence is bound (the count is derivable from the registry in one expression).

### F2 (MEDIUM): the repay action's own words promise more than the deployed vToken does

`guard.py:441-446` (`output_means`): "repayBorrow({amount}) extinguishes {amount} of debt … and hands back nothing. The floor equals the input for that reason"; the module docstring says the same at `:37-39`. Checked against Venus's own source and then against the deployed contract, that is not what the chain guarantees:

- **Venus caps a repay at what is owed.** `VToken.sol`, `repayBorrowFresh`: `vars.repayAmount = repayAmount >= vars.accountBorrows ? vars.accountBorrows : repayAmount;` (comment in source: "caps the repayAmount to the actual owed amount"). Verified **live on the deployed vUSDT**: `eth_call` of `repayBorrow(1)` from a fresh address with no debt and no allowance returned `0` (NO_ERROR) — under classic Compound semantics that call reverts in `doTransferIn` on the missing allowance; it can only succeed if the amount was first capped to zero. So if the debt shrank between draft and landing (a third-party repay, a partial liquidation), a mined, successful `repayBorrow(amount)` retires **less than `amount`, silently**. `min_output` as "debt retired" is a floor no chain mechanism enforces.
- **Venus fails without reverting.** `repayBorrowFresh` returns error codes (`failOpaque(Error.COMPTROLLER_REJECTION, …)`, `fail(Error.MARKET_NOT_FRESH, …)`) rather than reverting, and `mint` does the same — a transaction can succeed while the action did nothing. The module knows the return is an error code (`guard.py:66-67` says so) but never states the consequence.
- **The mint floor is likewise unenforceable on chain**: `mintFresh` computes `mintTokens` from the current exchange rate and takes no minimum-out parameter. Stage 2's headline property — the floor rides in the calldata, so the router re-enforces it even if everything off-chain is wrong — does **not** carry over to either Venus intent, and nothing in the record says so.

Nothing shipped can execute these intents, so this is not fund-safety today — it is the sentence a future armed path will trust. Fix is one sentence on each `output_means` (or in `ACTION_NOTE`): these floors are commitments recorded on the intent and enforced by no chain mechanism; Venus caps over-repays and signals failures in return codes and the Failure event, so whether `amount` was actually retired is read from the next account snapshot, not from transaction success.

### F3 (MEDIUM-LOW): the derived ratio's borrow side omits a debt Venus counts — minted VAI — and the cross-check text explains any gap as arithmetic

Venus's own liquidity figure includes VAI debt: `ComptrollerLens.sol` adds `vaiController.getVAIRepayAmount(account)` to `sumBorrowPlusEffects` after the per-market loop, and the deployed comptroller wires a live VAIController (read this session: `comptroller.vaiController()` = 0x004065D34C6b18cE4370ced1CeBDE94865DbFAFE). The guard's derivation (`assess`, `guard.py:300-308`) sums per-market rows only. Consequences for an account with minted VAI: `collateral_ratio` overstates health (VAI missing from the denominator), and `cross_check.difference_usd` equals the VAI debt — a systematic, diagnosable cause — while `CROSS_CHECK_METHOD` (`guard.py:128-140`) offers only truncation order and block skew as explanations and then, correctly, tells the reader to distrust the ratio. The design fails toward disclosure — the gap prints, `status` and the action trigger use Venus's shortfall verbatim so no action fires off the flattering number — but the method string's cause inventory is wrong for exactly the accounts where the check fires loudest. Fix: one sentence in `RATIO_METHOD` and `CROSS_CHECK_METHOD` naming minted VAI as a debt Venus counts and this derivation does not (or read `getVAIRepayAmount` into the state and subtract honestly). The fixture account had no VAI (read live: 0), which is why the builder's smoke saw only the 245-unit truncation gap.

## Tier 2 — recommended, non-blocking

### F4 (LOW): the direction map's guard does not pin the direction values

`intent.py:109-111` still decides with `if direction == "at_or_below": … else at-or-above`, and the new test (`test_execution_intent.py:91-97`) asserts `set(CONDITION_DIRECTIONS) == CONDITION_KINDS` — which cannot fail, since `CONDITION_KINDS` is defined as `frozenset(CONDITION_DIRECTIONS)` (`intent.py:56`) — plus `kind.endswith(direction)`. The endswith check has real bite for cross-assignments, but a future mapping of `"…_at_or_below"` to `"below"` or `"or_below"` passes it and silently evaluates at-or-above: the same shape of bug one level up. One line closes it: `assert set(CONDITION_DIRECTIONS.values()) == {"at_or_below", "at_or_above"}`.

### F5 (LOW): a drafted move's destination pool and its swap leg are never checked against each other

`plan_move` (`router.py:301-318`) refuses a destination outside the universe and assets off `MOVE_ASSETS`, but never checks that `token_out` is one of the destination pool's own two tokens — so a `MoveAction` can say `destination_pool` X (a USDT/USDC pool) while the committed swap buys WBNB, under a `not_built` sentence claiming the leg "gets the caller into the right asset" (`router.py:98-102`). The shipped test exercises exactly this shape without noticing (`test_yield_router.py:352-364`: USDC→WBNB "toward" a set whose top pool is USDT/USDC). Unreachable from the hire path, which never drafts (`_run_yield_router` passes no wallet); direct callers only. Fix: check `token_out` against the destination row's `token0/token1` ids, or soften the sentence.

### F6 (LOW): `preview(wallet=…)` routes to `candidates[0]` unconditionally

`router.py:432-441`: with a wallet named, the drafted leg targets the top-rate candidate whatever its own break-even says, the action record does not carry that candidate's `within_horizon` flag (it is in `candidates[]` but not bound to the action), and an empty universe raises `IndexError` rather than a stated refusal (`candidates[0]`); `amount`/`cap` left `None` raise `TypeError` inside `plan_move`. All unreachable from served paths (the hire never passes a wallet; the catalogue returns its own empty-universe answer first, `catalogue.py:239-249`). Cheap fixes: attach the chosen candidate's break-even to the action, and refuse an empty set with a sentence.

## The assigned questions, answered

**(a) The health-factor honesty line.** Holds everywhere I could reach. `AccountState` and `MarketPosition` carry no `health_factor` field (asserted at `test_venus_markets.py:247-253`); the assessment's key-scan test pins the phrase to exactly one key, `publishes_health_factor` (`test_venus_guard.py:219-228`); every assessment serves `publishes_health_factor: false` with the note, and the derived ratio always travels with `collateral_ratio_method` (formula, all five input sources, scales, truncation direction — `guard.py:113-123`), `collateral_ratio_scale` and `collateral_ratio_is_derived: true`. `assess` computes no ratio at all where there is no denominator, and says why (`NO_RATIO`). llms.txt (:522-528), SKILL.md (:328-331) and the registry card (`registry.py:63-66`) all state the absence in their first breath; the web layer paints from the API and authors nothing. The cross-check is **real and correct as an identity**: weighted collateral minus borrows is the same quantity as liquidity minus shortfall — confirmed against the lens's final branch (`sumCollateral > sumBorrowPlusEffects ? (liquidity, 0) : (0, shortfall)`), computed from the same row set (`getAssetsIn`, which is what the comptroller iterates), the same stored exchange rates and the same oracle. Its one blind spot is F3 (VAI), which enlarges the printed gap rather than hiding anything.

**(b) Can "highest APR" escape its universe?** No path found. Every comparison is drawn from `universe.included` only; the descriptor states size, considered, source, `observed_at`, both thresholds, allowlist size and every exclusion with gate and reason (`universe.py:75-90`), and the bound sentence defines what "highest" may mean (`UNIVERSE_BOUND`). Exclusion is total — every input row lands on one side or the other (`test_yield_universe.py:127-132`) — and missing fee data excludes rather than reading as a measured 0% (`_fee_data`, with the Stage 1e overstatement named). The ordering is by one named observed metric, stated in the payload (`ORDERING`), ties keeping the source's order (stable sort). `plan_move`'s destination allowlist **is** the universe (`router.py:301-307`), so a pool that failed the gate cannot be routed to whatever its rate; the hire path's baseline substitution is said in three honest variants (`catalogue.py:251-276`, test-pinned against the silent-substitution lie); an empty universe is its own stated answer on both the module and the hire path. Verified live: 24/30, six reasoned exclusions, bound sentence present.

**(c) Break-even honesty.** The code cannot filter: `preview` appends every candidate with its own `break_even` (`router.py:416-428` — no conditional anywhere), and `break_even` labels rather than drops (`within_horizon: false` with days stated, or with the no-extra reason). Tests hold it twice (`test_a_higher_rate_with_a_break_even_past_the_horizon_is_shown_and_labelled`; `test_every_candidate_in_the_preview_carries_its_own_break_even`, which fails if no beyond-horizon candidate exists in the fixture). Live this session with the defaults: 10 not-within-horizon candidates shown, of which **4 are the higher-APR-but-past-horizon kind** — Cake/WBNB net 0.0173 at 36.3 days, USDT/USD1 at 175.2, USDT/USDC at 259.0, slisBNB/WBNB at 464.1 — all present, all labelled. The builder's smoke claim is confirmed in kind and, allowing for a day's market movement, in detail. The arithmetic (`cost / (position × Δapr / 365)`) is dimensionally right and stated inline with its horizon named as a choice. Residue: F6 (the *drafted move* ignores the label it ships beside).

**(d) The conservative-action boundary.** Genuinely no execution path. The module's write surface is two encodable functions, asserted as a set (`WRITE_ABI` = {repayBorrow, mint}, `test_venus_guard.py:308-317`) with a source scan for `borrow(uint256)`, `redeem(`, `redeemUnderlying`, `exitMarket`; `plan_actions` drafts only through `_repay`/`_supply`, only into entered markets, only when **Venus itself** reports shortfall ≥ the policy trigger (`guard.py:386` — the guard cannot invent urgency; a trigger of zero is refused at policy construction). `HealthGuardPreview` holds a reader and a policy and nothing else; there is no armed class in the module (the grep and the attribute test agree), no `submitter`/`signer`/`authority` anywhere in `agents/venus/` or `agents/yield_router/`, and the repository's only submission call site remains the grid operator's — unchanged this stage. The catalogue constructs the preview class only (`catalogue.py:190-214`). One property worth recording: a future path naively feeding a repay intent through the Stage 2 `simulate()` fails closed — the degenerate route `(underlying, underlying)` makes the router quote revert (identical addresses) — so even the wrong reuse refuses rather than fires.

**(e) The `min_output` overload — ruling: ACCEPTABLE, conditional on F2's sentence.** The kernel's floor invariant from Stage 2 is two claims. The first — *no intent constructs without a positive floor; "whatever comes back" is unreachable* — survives intact: the repay floor is the positive amount, the mint floor is quote-with-haircut and refuses at zero (`guard.py:462-467`), and both pass through `ActionIntent`'s own validation unchanged. The second — *the floor is carried in the calldata, so the chain re-enforces it even if everything off-chain is wrong* — was always a property of the **swap** shape, and it does not and cannot transfer to Venus: `repayBorrow` caps rather than reverts and `mint` has no minimum-out parameter (both verified, source and live). The reinterpretation itself is done the right way: stated per-action in `output_means` in exactly the words needed ("not a token received… the floor equals the input"), the degenerate route makes the record self-describing, `slippage_bps: 0` is justified in-band, and the builder put the sentence on a wrapper (`GuardAction`) rather than widening the kernel — the minimal honest shape, since a kernel field for output semantics is Stage-4 surgery nobody sanctioned. What weakens the invariant is not the overload but the **silence about enforcement**: a reader who learned on Stage 2 that `min_output` is a chain-enforced floor will assume these are too, and for both Venus intents nothing enforces them — worse, a successful transaction can retire less than the floor (the cap) or nothing (the error-code returns). With F2's one-sentence disclosure on each action, the overload is honest and I would not ask for more. Without it, the field borrows Stage 2's credibility for a floor nothing stands behind — which is precisely the class of claim this project refuses. So: accept the semantics, require the sentence.

**(f) The kernel edit and the latent bug.** The bug was real and exactly as described: the pre-edit `holds()` was `if kind == "price_at_or_below": <= else: >=` (read from the diff), correct for the two kinds that existed and wrong for every future `_at_or_below` kind — latent, not reachable, in Stage 2. The fix is correct: direction lookup, `CONDITION_KINDS` derived from the map so an unmapped kind cannot construct (`Condition.__post_init__` checks membership, so the `holds()` lookup cannot KeyError), the new `shortfall_at_or_above` mapped at-or-above consistently with `plan_actions`' own gate (`shortfall < trigger → []`, both inclusive), and the condition's subject/threshold are re-evaluable by a reader (verbatim shortfall, 1e18 USD). The edit was not in the plan but was necessary for Task 2 (the closed set would have refused the kind) and is disclosed in the comment block. Residue: the guard test is weaker than the claim — the mapped-ness assertion is a tautology and the direction *values* are unpinned (F4).

**(g) `agrees` → `exactly_equal`.** The rename is right, and it masks nothing — it removes a judgement rather than adding one. The two computations genuinely cannot be expected to agree to the unit: the lens truncates at different points than the guard (confirmed from source; three reordered floor-divisions per market), and the two reads can land at different blocks — so a field named `agrees` must either lie about correct derivations (the builder's observed 245-unit case) or smuggle in an unstated tolerance. `exactly_equal` reports the primitive fact; `difference_usd` prints beside both magnitudes; and the method text draws the line a reader needs ("a difference of that size is arithmetic; a difference near the magnitudes themselves is a reason to distrust the ratio") without choosing a numeric threshold, which is the honest refusal — a tolerance would be a judgement this record correctly declines to make. A real disagreement is *more* visible under the new semantics, not less: nothing rounds, nothing suppresses, `exactly_equal: false` plus a large printed difference is the alarm. The one incompleteness is F3's cause inventory. The 245-unit observation itself: mechanism verified, number unreproducible (F12).

**(h) Reuse, not forking.** Verified. The universe gates through `pancake.pools.is_plausible` and carries its reasons verbatim (one added gate, fee-data, for the thing a comparison needs and a plausibility check does not); the router's rates are `pools.net_fee_apr`/`turnover`; the swap leg is built from `execution.simulate.swap_calldata` against the same `PANCAKE_V2_ROUTER` with the same quote-minus-bps floor shape as the grid, and every intent on both services is a Stage 2 `ActionIntent` through `commit()` — asserted by tests on both (`test_the_intents_are_the_stage_two_kernel…`, `test_a_move_is_one_swap_leg_built_through_the_stage_two_kernel`). `VenusReader` reuses `escrow.chain.Rpc` for failover rather than a fourth copy. No second execution path exists to fork (see d).

**(i) Thesis regressions.** One found — F1, the stale identity count, the same species as the two the builder caught. Beyond it: every rate on every surface carries window and denominator (`RATE_WINDOW`/`RATE_DENOMINATOR` on each candidate; the trigger and both Venus figures carry their 1e18 scales; the ratio carries scale and method); no verdict vocabulary in any new served string (value-level scans extended over both services' full previews, the universe record, and — via the Stage 1 machinery — the new cards; a manual read concurs); no counterfactual anywhere (`BANNED_CLAIMS` scanned over every string the guard emits, word-boundary-safe); the inventory sentences are corrected **and bound in both directions** (the llms.txt guard now holds the all-stocked branch and the emptied branch, and the two empty-state tests were rewritten to monkeypatch the registry empty so they keep testing after the shelves stocked — the right response to a guard that would otherwise rot into a no-op). SKILL.md's counts are all stable facts. The six-service enumeration at llms.txt:493 is exact.

**(j) The three network calls where one was sanctioned.** Justified, and I would have objected to the opposite. All three were read-only in the classes this repository already uses (eth_call, explorer HTTPS); the plan's "ONE live read" sat in Task 1, and the two beyond it are the reads that caught vBNB's empty-`underlying()` decode trap (a market that exists reading as an endpoint outage — confirmed live here: the call succeeds and returns no bytes) and the truncation gap that forced the `agrees` rename (mechanism confirmed from source here).
