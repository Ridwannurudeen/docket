Nothing was accepted, deferred, or suppressed, so this file records no advisory ids and no

## How to reproduce it

```bash
uv export --quiet --frozen --extra dev --no-emit-project --format requirements.txt \
  --output-file /tmp/audit-requirements.txt
pip-audit --strict --disable-pip --require-hashes --progress-spinner off \
  -r /tmp/audit-requirements.txt
```

The audit reads the lock rather than an installed environment, for two reasons. A `uv sync`
environment has no `pip` in it, and `pip-audit`'s environment mode needs one. More
importantly, the lock is the set every machine installs; whatever a particular runner
resolved is not.

`--strict` fails the run if any distribution could not be audited, so a package that silently
dropped out of the check cannot be reported as a package with no findings. `--require-hashes`
makes the audit read the file as fully pinned rather than re-resolving it, which is why
`--disable-pip` costs nothing.

CI runs exactly this as the `audit` job in `.github/workflows/ci.yml`, so a newly published
advisory against a pinned version fails the next build rather than waiting for someone to
repeat this by hand.

## If a future run finds something

Record it here in the same shape: the advisory id, the affected distribution and version, the
fixed version if one exists, and one of two decisions.

- **Upgrade within the pins.** Change the pin in `pyproject.toml` or let `uv lock` move a
  transitive version, regenerate `uv.lock`, and confirm
  `deploy/runtime-requirements.txt` is regenerated by the `package` job's own export check.
- **Documented acceptance.** Only with the reason stated in terms of this codebase — which
  code path reaches the vulnerable function, and why it cannot be reached here — plus the
  date the decision should be revisited. An acceptance with no reachability argument is a
  suppression, and this file is not for suppressions.
